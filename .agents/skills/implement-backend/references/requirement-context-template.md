# Backend Requirement Context Template

이 문서는 `implement-backend`가 요구사항 명확화 게이트를 통과한 뒤 저장하는 확정 요구사항 컨텍스트 artifact의 템플릿을 정의한다.

## 문서 역할

확정 요구사항 컨텍스트는 메인 에이전트가 작성하는 공통 입력 artifact다.

목적은 업무 규칙, 정책, 상태 변화, 운영 요구사항을 명확히 정의하여 Backend Design Writer와 Implementation Engineer가 추가 해석 없이 시스템을 설계·구현할 수 있게 하는 것이다.

- 요구사항 명확화 기준은 [requirement-clarification-gate.md](requirement-clarification-gate.md)가 소유한다.
- run 저장 위치와 파일명 규칙은 [run-artifact-protocol.md](run-artifact-protocol.md)가 소유한다.
- design/implementation/review input에서 이 파일의 경로를 참조한다.
- 각 서브에이전트는 이 파일에 없는 업무 규칙, 정책, 상태 변화, 운영, 실패 처리, 정합성, 재처리, 동시성 정책을 임의로 확정하지 않는다.

## 저장 위치

run 전체에 같은 요구사항 경계를 적용할 수 있으면 아래 경로를 권장한다.

```text
.agents/runs/{run_id}/inputs/requirement-context.v1.md
```

마일스톤별로 요구사항 경계가 다르면 아래 경로를 사용한다.

```text
.agents/runs/{run_id}/inputs/M{n}/requirement-context.v1.md
```

## Template

````markdown
# Backend Requirement Context

## Metadata

```yaml
schema_version: implement-backend-requirement-context/v1
run_id: <run_id>
milestone: <all | M<n>>
created_at: <ISO-8601 timestamp>
source_request: <사용자 요청 요약>
```

## 요청 요약

- 사용자가 요청한 backend 변경을 한 문단으로 요약한다.
- 원문 요청의 핵심 의도와 이번 run에서 다룰 문제를 분리한다.

## 업무 목표

- 사용자 또는 내부 시스템 관점에서 달성해야 하는 업무 결과를 기록한다.
- 성공으로 간주할 수 있는 observable backend 결과를 적는다.

## 범위와 제외사항

- 이번 run 또는 마일스톤에 포함할 도메인, API, UseCase, storage, external integration 범위를 기록한다.
- 명시적으로 제외할 동작, 정책, API, DB/schema, 후속 작업을 기록한다.

## 액터와 유저 플로우

- 기능을 사용하는 주체와 호출 주체를 기록한다.
- 요청 전제, 주요 흐름, 예외 흐름을 업무 순서대로 기록한다.

## 업무 규칙

- 허용 조건, 금지 조건, 계산 규칙, 승인 조건, 권한 조건, 제한 조건을 기록한다.
- 사용자 또는 Source of Truth로 확정된 도메인 규칙만 포함한다.

## 정책 결정

- 삭제, 보관, 노출, 승인, 취소, 재처리 허용, 감사, 알림 같은 제품·운영 정책을 기록한다.
- 정책이 확정되지 않았으면 이 섹션에서 임의로 정하지 않고 `남은 미결정 사항`으로 보낸다.

## 상태 변화

- 가능한 상태와 상태 전이 조건을 기록한다.
- 상태 전이를 일으키는 주체, 실패 시 기대 상태, 되돌릴 수 있는 상태를 기록한다.

## 정합성 요구사항

- 반드시 함께 성공하거나 함께 실패해야 하는 업무 단위를 기록한다.
- 부분 성공 허용 여부, 최신성 요구, 후속 처리 지연 허용 여부를 기록한다.

## 동시성 요구사항

- 중복 요청, 동시 변경, 순서 보장, 같은 대상에 대한 경합이 있는지 기록한다.
- 동시에 발생한 요청이 사용자에게 어떤 결과로 보여야 하는지 기록한다.

## 후속 처리 요구사항

- 요청 안에서 즉시 완료되어야 하는 일과 요청 이후 지연 처리되어도 되는 일을 구분한다.
- 후속 처리가 누락되거나 지연될 때 허용 여부와 사용자 영향도를 기록한다.

## 실패 처리 요구사항

- 실패 시 사용자에게 즉시 실패로 보여야 하는지, 나중에 복구되어도 되는지 기록한다.
- 자동 재시도 기대, 수동 복구 필요 여부, 부분 실패 허용 여부를 기록한다.

## 운영 요구사항

- 실패 추적, 재처리, 감사 로그, 관리자 개입, 알림, 모니터링 요구를 기록한다.
- 운영자가 확인해야 하는 정보와 조치해야 하는 상황을 기록한다.

## 데이터와 조회 요구사항

- 예상 데이터 규모, 증가 속도, 보관 기간, 조회 빈도를 기록한다.
- 조회 주체, 필터, 정렬, 검색, 최신성, 정확도 요구를 기록한다.

## 성능 요구사항

- 응답 시간, 처리량, 대량 처리 기준, 동시 요청 수준 등 명시 요구를 기록한다.
- 명시 요구가 없으면 `없음`으로 쓰고 임의 목표를 만들지 않는다.

## 외부 계약

- frontend, 외부 시스템, 다른 backend 모듈이 소비하거나 제공해야 하는 계약을 기록한다.
- 요청/응답 필드, 상태 코드, 이벤트 의미, 미확정 계약을 구분한다.

## 검증 기준

- 요구사항 충족 여부를 확인할 compile/test/manual verification 기준을 기록한다.
- 검증할 수 없는 정책은 별도 미결정 사항으로 남긴다.

## 사용자 확인 필요 없음

- 코드베이스 관례로 처리해도 되는 구현 선택을 기록한다.
- 패키지 구조, naming, DTO/UseCase/repository 패턴, validation/error/logging 적용 방식처럼 저장소 관례로 충분히 결정 가능한 항목만 포함한다.

## 금지된 추론

- 아직 확정되지 않아 구현, 설계, 리뷰에 반영하면 안 되는 정책을 기록한다.
- 특히 업무 규칙, 상태 변화, 운영 정책, 실패 처리, 정합성, 재처리, 동시성, 후속 처리 유실 허용 여부, 감사 로그 필요 여부는 사용자 또는 Source of Truth 없이 확정하지 않는다.

## 남은 미결정 사항

- 이번 마일스톤에서 제외하거나 사용자 확인이 필요한 항목을 기록한다.
- 구현을 차단하는 항목과 후속 마일스톤으로 넘길 수 있는 항목을 구분한다.
````

## 작성 규칙

- 빈 섹션은 `없음`으로 명시한다.
- 추론한 저장소 관례는 업무 요구사항 섹션이 아니라 `사용자 확인 필요 없음`에 둔다.
- 업무 규칙, 정책, 상태 변화, 운영 요구사항은 가능한 한 구체적인 조건과 기대 결과로 작성한다.
- 기술 선택은 기록하지 않는다. 기술 판단에 필요한 업무·운영·정합성 제약만 기록한다.
- 설계 판단에 영향을 주는 미확정 정책은 `금지된 추론` 또는 `남은 미결정 사항`에 둔다.
- role input artifact에는 이 문서의 본문을 복사하지 않고 경로만 기록한다.
